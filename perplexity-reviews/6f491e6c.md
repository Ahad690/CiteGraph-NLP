# Code Review: 6f491e6c

> Handle failed and partial run states without crashing

## Summary

This commit hardens `DashboardRoute` against partial backend payloads for in-progress or failed analysis runs. The new `withDefaults()` helper fills missing `RunResult` collection fields with empty arrays, preventing dashboard pages from crashing when the backend returns only `{run_id, status, error, created_at}` (`frontend/src/components/layout/DashboardRoute.tsx:L16-L32`). It also adds a dedicated failed-state UI with the backend error message and a link back to `/start` (`frontend/src/components/layout/DashboardRoute.tsx:L50-L64`), while preserving the existing processing/loading behavior.

## Issues & Suggestions

- **Good defensive normalization**  
  `frontend/src/components/layout/DashboardRoute.tsx:L16-L32` correctly defaults all array fields used by downstream pages: `papers`, `population_resolutions`, `population_candidates`, `citation_edges`, `ranked_foundational_papers`, `ranked_paths`, and `warnings`. This directly fixes the “Cannot read properties of undefined (reading 'length')” class of crashes.

- **Potentially incomplete `RunResult` defaults**  
  `frontend/src/components/layout/DashboardRoute.tsx:L16-L32` only defaults fields shown in this diff. If `RunResult` also includes fields like `metrics`, `pipeline`, `exports`, `seed_query`, or other optional objects used by dashboard subpages, those pages may still crash. Consider centralizing this normalizer near the API layer and ensuring it covers the full `RunResult` schema.

- **Type cast hides API/schema mismatch**  
  `frontend/src/components/layout/DashboardRoute.tsx:L47` casts `query.data` to `Partial<RunResult> & { run_id: string; status: string }`. This is pragmatic, but it bypasses compile-time validation. A better long-term fix is to define an explicit union type such as `RunResult | RunStatusPayload | RunFailedPayload`.

- **Failed-state error message may expose backend internals**  
  `frontend/src/components/layout/DashboardRoute.tsx:L58` displays the backend `error` string directly. That is useful for debugging, but if backend errors include stack traces, provider URLs, tokens, filesystem paths, or raw exception text, they may leak implementation details to users. Prefer a safe backend error message plus optional diagnostic ID if available.

- **Failed-state UX is a clear improvement**  
  `frontend/src/components/layout/DashboardRoute.tsx:L52-L63` gives users a concrete next action instead of a broken dashboard. The “Try a different paper” CTA is appropriate and keeps the recovery path simple.

- **Processing-state behavior remains safe**  
  `frontend/src/components/layout/DashboardRoute.tsx:L67-L68` now checks `run.papers.length` after normalization, so partial processing payloads no longer crash even when `papers` is omitted.

## Security & Performance

Security risk is low, but displaying raw backend error messages in the UI (`frontend/src/components/layout/DashboardRoute.tsx:L58`) should be reviewed to ensure sensitive internals are not exposed. Performance impact is negligible; `withDefaults()` allocates a small normalized object per render. Scalability is unaffected.

## Overall Score: 9/10

This is a strong frontend robustness fix that addresses a real runtime crash and improves failed-run UX. The main remaining concern is that normalization is local and manually mirrors the schema, which can drift, plus raw backend error rendering should be sanitized or standardized.

## Recommendations

1. Move `withDefaults()` into the API/data layer so every consumer receives a normalized `RunResult`.  
2. Define a typed API union for completed, processing, and failed run payloads instead of casting at `DashboardRoute.tsx:L47`.  
3. Ensure backend `error` values shown at `DashboardRoute.tsx:L58` are user-safe.  
4. Add tests for failed, processing-with-minimal-payload, and completed payload states.
