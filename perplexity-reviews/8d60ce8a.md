# Code Review: 8d60ce8a

> Move Nginx backups out of sites-enabled

## Summary

This commit fixes an important Nginx deployment issue in `.github/workflows/deploy-backend.yml`: previous backups were written directly into `/etc/nginx/sites-enabled`, and Nginx loads all files there, including `.bak.*` files. The workflow now removes stray backup files from `sites-enabled`, creates `/etc/nginx/backups`, and stores new backups there instead (`.github/workflows/deploy-backend.yml:L112-L116`). This prevents stale or broken backup configs from participating in `nginx -t`.

## Issues & Suggestions

- **Positive: backup location is now correct**  
  Moving backups out of `/etc/nginx/sites-enabled` is the right fix (`.github/workflows/deploy-backend.yml:L115-L116`). Nginx commonly includes everything from `sites-enabled`, so keeping backups there can absolutely break validation.

- **Risk: broad deletion in `sites-enabled`**  
  `rm -f /etc/nginx/sites-enabled/*.bak.* /etc/nginx/sites-enabled/leadgen.bak.disabled` (`.github/workflows/deploy-backend.yml:L113`) is pragmatic cleanup, but it permanently deletes files without logging what was removed. Consider `find ... -print -delete` so deploy logs show exactly what was cleaned up.

- **Backups are created but still not used for rollback**  
  The backup is now safely stored (`.github/workflows/deploy-backend.yml:L116`), but the later `nginx -t` failure path still does not restore it. The backup should be assigned to a variable like `BACKUP_PATH=...` and restored if validation fails.

- **Potential unbounded backup growth**  
  `/etc/nginx/backups` will accumulate timestamped backups indefinitely (`.github/workflows/deploy-backend.yml:L115-L116`). Add retention cleanup, such as keeping the last 10 backups or deleting backups older than 30 days.

- **Good: cleanup happens before new mutation**  
  Cleaning stale backups before editing (`.github/workflows/deploy-backend.yml:L112-L116`) is correct because old `.bak.*` files can keep `nginx -t` failing even if the active config is repaired.

## Security & Performance

Security impact is low and positive: fewer stale Nginx configs are accidentally loaded. Performance impact is negligible; this is deploy-time cleanup only. Operationally, this reduces Nginx validation failures, but rollback and retention are still needed for a safer deployment story.

## Overall Score: 8.5/10

This is a targeted and correct fix for a real Nginx behavior issue. It improves deployment reliability significantly, but it should be followed by rollback-on-failure and backup retention cleanup.

## Recommendations

1. Store the backup path in `BACKUP_PATH` and restore it if `nginx -t` fails.  
2. Log deleted backup files before removing them.  
3. Add retention cleanup for `/etc/nginx/backups`.  
4. Keep backups outside all Nginx include paths permanently.  
5. Add a post-reload health check for `/citegraph/health`.
