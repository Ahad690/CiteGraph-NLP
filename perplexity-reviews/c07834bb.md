# Code Review: c07834bb

> Add HTTPS reverse proxy via Caddy for backend

## Summary

This commit adds HTTPS support for the backend via a Caddy reverse proxy to prevent mixed content issues with the Firebase-hosted frontend. Key changes include: adding a `Caddyfile` template using the `BACKEND_DOMAIN` environment variable (Caddyfile:L1-L3), modifying the backend GitHub Actions deploy workflow to install and configure Caddy if `BACKEND_DOMAIN` is set (`.github/workflows/deploy-backend.yml:L106-L138`), and updating the frontend CI build to use `https://BACKEND_DOMAIN` as `VITE_API_BASE` (`.github/workflows/deploy-frontend.yml:L30`), with a fallback to the previous IP if the secret is missing.

## Issues & Suggestions

- **Caddy Installation in CI Deploy Script**:  
  Installing Caddy dynamically on every deployment (`deploy-backend.yml:L110-L116`) may be fragile:
  - Repeated `apt-get update` and install can fail if package sources change.  
  - Consider pre-baking Caddy into the backend Docker image to simplify deployment.

- **Environment Variable Expansion in Caddyfile**:  
  Using `{$BACKEND_DOMAIN}` in `Caddyfile:L1` relies on the systemd environment override (`domain.conf:L5`). Confirm that Caddy reads this variable at runtime—otherwise, the reverse proxy might fail. Explicitly templating the domain in the Caddyfile during CI build could be safer.

- **Fallback Logic for Frontend Build**:  
  `.github/workflows/deploy-frontend.yml:L30` uses `${{ secrets.BACKEND_DOMAIN && format('https://{0}', secrets.BACKEND_DOMAIN) || 'http://46.225.8.77:8002' }}`. This is clever, but:
  - GitHub Actions expressions do not fully support inline logical operators in all runners; confirm parsing works.  
  - Consider separating into a separate step that writes `.env.production` to ensure Vite reads it correctly.

- **No HTTPS Redirect / Security Headers**:  
  The Caddyfile simply reverse-proxies to HTTP (`reverse_proxy localhost:8002`). It would be better to:
  - Enforce HTTPS-only (Caddy can handle automatically).  
  - Add `Strict-Transport-Security` and other security headers to prevent downgrade attacks.

- **No Validation of Domain / ACME Challenges**:  
  The workflow assumes the DuckDNS domain resolves and ACME certificates will issue automatically. Failures in DNS propagation or ACME issuance are not handled; consider logging or retry logic.

- **Systemd Environment Override Cleanup**:  
  Overwriting `/etc/systemd/system/caddy.service.d/domain.conf` may persist stale environment variables between deploys if the domain changes. A safer approach is to template the Caddyfile fully with the domain before copying.

## Security & Performance

- **Security**: Switching frontend to HTTPS resolves mixed content issues (`deploy-frontend.yml:L30`). Adding HSTS and secure headers in Caddy would improve protection.  
- **Performance**: Reverse proxy adds minimal latency; acceptable for this scale. Installing Caddy on every deploy may slightly slow deployment (~30-60s).  
- **Scalability**: Single backend instance with Caddy works for low traffic. If scaling horizontally, consider using a load balancer or Docker network with Caddy in front of multiple backend containers.

## Overall Score: 8.5/10

This commit addresses a critical HTTPS and mixed content issue, but the CI-based Caddy installation and reliance on environment variable substitution are brittle. Some security hardening and templating improvements could make it more robust.

## Recommendations

1. Pre-bake Caddy into the backend Docker image to avoid dynamic installation (`deploy-backend.yml:L110-L116`).  
2. Template the `Caddyfile` during CI build with the domain instead of relying solely on systemd environment expansion.  
3. Add HTTPS-only redirects and security headers (HSTS, X-Content-Type-Options, X-Frame-Options) in the Caddy configuration.  
4. Validate ACME certificate issuance and log errors if domain resolution fails.  
5. Consider separating domain configuration into a `.env.production` file for frontend build to ensure Vite picks it up reliably.  
6. Document the requirement for `BACKEND_DOMAIN` secret and DuckDNS setup in README/USER_GUIDE.  

This approach ensures robust HTTPS connectivity, reduces deploy-time failures, and improves maintainability.
