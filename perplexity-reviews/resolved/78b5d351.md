# Code Review: 78b5d351

> Debug Nginx config and inline the citegraph location block

## Summary

This commit modifies `.github/workflows/deploy-backend.yml` to add heavy Nginx diagnostics during deployment and reverts from the safer include-file approach back to directly injecting a `/citegraph/` location block into the discovered Nginx config. It prints matching config paths, directory listings, the full current config, and the updated config to CI logs before running `nginx -t` and reloading Nginx (`.github/workflows/deploy-backend.yml:L105-L136`). The goal is clearly debugging the live server’s unknown Nginx structure, but the implementation introduces production deployment risks.

## Issues & Suggestions

- **High risk: full Nginx config is printed to CI logs**  
  `.github/workflows/deploy-backend.yml:L116-L117` and `.github/workflows/deploy-backend.yml:L124-L125` print the entire Nginx config before and after modification. Nginx configs often contain internal upstreams, domain layout, certificate paths, auth headers, paths, and operational details. This is too much for normal deploy logs. Prefer printing only `grep -n` context around `server_name` and `location` blocks, or guard full dumps behind a temporary debug flag.

- **The workflow logs an error but does not fail when no config is found**  
  `.github/workflows/deploy-backend.yml:L133-L134` prints `ERROR: No nginx config found for hetzner-api`, but the script exits successfully because there is no `exit 1`. That can produce a green deploy while the API route is still broken. This should fail fast.

- **Direct `sed` injection is brittle and can produce invalid Nginx syntax**  
  `.github/workflows/deploy-backend.yml:L121` injects a multiline `location` block after any `server_name.*hetzner-api` line. If the config has multiple matching server blocks, inline comments, one-line server blocks, or includes, this may insert in the wrong place or duplicate across HTTP/HTTPS blocks. The prior include-file approach was safer; the remaining issue was locating the right include point.

- **Live config is modified before validation, with no rollback**  
  `.github/workflows/deploy-backend.yml:L121-L129` modifies the active config, then runs `nginx -t`. If validation fails, the invalid file remains on disk. Nginx may continue serving the old in-memory config, but the next reload/restart can fail unexpectedly. Create a backup, write to a temp copy, validate, then atomically replace.

- **Potential shell expansion issue in inserted Nginx variables**  
  `.github/workflows/deploy-backend.yml:L121` contains `$host`, `$remote_addr`, `$proxy_add_x_forwarded_for`, and `$scheme` inside a double-quoted `sed` script context inherited from the shell script. In Bash, those may expand to empty shell variables before reaching the file unless escaped. The earlier heredoc/include approach with quoted heredoc was safer. These should be written as `\$host`, `\$remote_addr`, `\$proxy_add_x_forwarded_for`, and `\$scheme`, or generated via a single-quoted heredoc.

- **Idempotency check is too broad**  
  `.github/workflows/deploy-backend.yml:L119` checks only for `/citegraph/`. This avoids duplicate route insertion, but it can falsely skip if `/citegraph/` appears in a comment or unrelated block. Check for `location /citegraph/` specifically.

- **Positive: `nginx -t` before reload is the right validation step**  
  `.github/workflows/deploy-backend.yml:L128` correctly validates Nginx before reload. Keep this, but pair it with temp-file validation and rollback so failed validation does not leave bad config on disk.

## Security & Performance

Security risk is the biggest concern here: dumping full Nginx config to CI logs (`.github/workflows/deploy-backend.yml:L116-L125`) may expose infrastructure details. The proxy route itself is fine conceptually: `/citegraph/` forwards to `127.0.0.1:8002` (`.github/workflows/deploy-backend.yml:L121`), keeping the backend bound locally. Performance impact is negligible, but deployment reliability is at risk because live config is edited without backup or rollback.

## Overall Score: 6.5/10

This is useful as a one-off diagnostic patch, but it is not production-grade deployment code. The broad config logging, brittle inline `sed`, possible `$host` variable expansion bug, lack of rollback, and non-failing error path all need correction before this should live in the main workflow.

## Recommendations

1. Replace full `cat "$NGINX_CONF"` dumps with targeted diagnostics around `server_name`, `listen`, and existing `location` blocks.  
2. Fail the workflow with `exit 1` if no matching Nginx config is found.  
3. Restore the include-file strategy, but insert the include safely into a temp copy of the correct server block.  
4. Escape Nginx variables or use a single-quoted heredoc when generating proxy config.  
5. Back up the config, validate with `nginx -t`, and restore on failure.  
6. Add a post-deploy check for `https://hetzner-api.duckdns.org/citegraph/health`.
