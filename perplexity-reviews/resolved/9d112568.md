# Code Review: 9d112568

> Strengthen tests: replace silent if-skip with hard assertions

## Summary

This commit substantially improves the API test suite by replacing silent `if status_code == 200` skips with deterministic fixtures, hard assertions, and polling. The new `completed_run_id` fixture pre-populates a completed `RunResult`, allowing graph/export tests to assert exact response shape and content without relying on the async pipeline (`tests/test_api_comprehensive.py:L135-L217`). It also adds `wait_for_status()` to poll background runs to observable/terminal states (`tests/test_api_comprehensive.py:L23-L45`) and mocks Crossref/Europe PMC to avoid slow retry behavior from unhandled provider calls (`tests/test_api_comprehensive.py:L239-L262`).

## Issues & Suggestions

- **Strong improvement: graph/export tests now fail when endpoints break**  
  `tests/test_api_comprehensive.py:L541-L570` and `tests/test_api_comprehensive.py:L582-L628` replace the previous conditional assertions with hard status-code and payload assertions. This directly fixes the earlier weakness where graph/export failures could be silently ignored.

- **Good deterministic fixture design for read endpoints**  
  `_build_completed_result()` at `tests/test_api_comprehensive.py:L135-L203` creates a stable completed run with known papers, citation edge, population resolution, and ranking. This is the right approach for testing read/export formatting separately from pipeline success.

- **`completed_run_id` uses a fixed run ID and may conflict if fixture scope changes later**  
  `tests/test_api_comprehensive.py:L207-L217` always writes `"deterministic-test-run"`. It is safe with the current per-test store reset, but brittle if fixture scope or store isolation changes. Consider deriving from `uuid.uuid4()` or `request.node.name` while still using deterministic data.

- **`wait_for_status()` mutates the response payload in-place**  
  `tests/test_api_comprehensive.py:L37-L38` injects `last["status"] = "completed"` into the decoded response object. That is fine locally, but it blurs the distinction between API shape and test helper shape. Safer: return `{"status": "completed", "payload": last}` or compute `observed_status` separately.

- **Polling helper can hide a completed-response schema regression**  
  `tests/test_api_comprehensive.py:L36-L38` treats any payload with `"papers"` and no `"status"` as completed. If the backend accidentally returns partial/malformed completed data with `papers: []` but missing required fields, `wait_for_status()` may call it completed. The later tests partly cover this, but the helper should probably require `"seed_paper_id"` and `"citation_edges"` too for RunResult detection.

- **Provider mock comments are helpful, but one import is unused**  
  `tests/test_api_comprehensive.py:L242` imports `re as _re` but never uses it. Remove it to keep lint clean.

- **Crossref mock response is semantically odd for a 404**  
  `mock_crossref_404()` at `tests/test_api_comprehensive.py:L239-L246` returns `status_code=404` with JSON body `{"status": "ok", ...}`. This is acceptable if the provider only cares about HTTP status, but it can make debugging confusing. Prefer a realistic error payload, or rename the helper to `mock_crossref_not_found()` and make the body match the failure.

- **Live pipeline tests still accept failure as success**  
  `tests/test_api_comprehensive.py:L793-L813`, `L817-L839`, and `L842-L858` accept either `"completed"` or `"failed"`. That is better than silent endpoint skipping, but it still does not prove the mocked happy path completes. Since `setup_all_provider_mocks()` now exists, at least one test should assert `completed` with the fixture mocks, otherwise a pipeline regression that always fails could still pass.

- **`test_get_run_status_after_start` may pass before meaningful work starts**  
  `tests/test_api_comprehensive.py:L506-L511` waits for `{"running", "completed", "failed"}`. If the goal is “observable after POST,” this is fine. If the goal is “background task starts,” consider asserting transition away from `"started"` explicitly, or rename the test to make the weaker contract clear.

- **Clamping tests still do not verify actual clamped values**  
  The comment at `tests/test_api_comprehensive.py:L652-L656` honestly says the API response cannot observe the clamped value. `test_clamping_is_silent_not_rejection()` at `tests/test_api_comprehensive.py:L711-L728` validates acceptance, not clamping. That is useful, but the test name overpromises. Add a lower-level request-model or route-unit test if clamped values matter.

- **Good new negative coverage for pending runs**  
  `tests/test_api_comprehensive.py:L572-L577` and `tests/test_api_comprehensive.py:L639-L645` correctly verify that existing runs without `result_json` return 404 for graph/export endpoints instead of pretending there is empty output.

- **Exact CSV assertions are useful but may be too format-coupled**  
  `tests/test_api_comprehensive.py:L597-L606` asserts exact header prefix and row count. This is good for contract tests, but future additions to CSV columns will break tests even if backward-compatible. If CSV is a public contract, keep it. If not, assert required columns by parsing the header instead.

## Security & Performance

Security impact is positive: stronger tests reduce the chance of shipping broken error paths or malformed export responses. There are no direct production code security changes. Performance-wise, `mock_crossref_404()` and `mock_europe_pmc_empty()` at `tests/test_api_comprehensive.py:L239-L262` should reduce test runtime by avoiding provider retry delays. The remaining performance risk is test flakiness/time from live pipeline polling at `tests/test_api_comprehensive.py:L793-L858`; deterministic fixture tests are fast, but the pipeline tests still depend on background scheduling and mocked provider completeness.

## Overall Score: 8.5/10

This is a strong test-quality improvement. The deterministic completed-run fixture and hard assertions directly address the prior silent-skip problem. The main remaining gap is that live pipeline tests still allow `"failed"` as an acceptable outcome, so they prove lifecycle stability but not a successful mocked pipeline.

## Recommendations

1. Add one live pipeline test that must reach `"completed"` using `setup_all_provider_mocks()` (`tests/test_api_comprehensive.py:L793-L813`).  
2. Change `wait_for_status()` to avoid mutating response JSON and tighten RunResult detection (`tests/test_api_comprehensive.py:L23-L45`).  
3. Remove the unused `_re` import in `mock_crossref_404()` (`tests/test_api_comprehensive.py:L242`).  
4. Rename or split clamping tests so “accepted out-of-range inputs” and “actual clamped values” are separately verified (`tests/test_api_comprehensive.py:L652-L728`).  
5. Consider generating a unique completed run ID per test to future-proof `completed_run_id` (`tests/test_api_comprehensive.py:L207-L217`).
